# CodeRisk 项目需求说明

更新：2026-10-25。本文说明项目目标，待讨论的实现细则见决策记录。

## 1. 我们要做一个什么项目

CodeRisk 是一个帮助开发团队审查 GitHub 代码修改的 AI 工具，有自己的网页端。

当开发者提交 Pull Request（PR，即请求把一组修改合并到项目）时，CodeRisk 获取这次修改，找到相关 Python 函数，结合静态规则和 AI 分析，给出值得人工检查的潜在问题。

结果既能在 CodeRisk 网页中查看，也能作为总体评论出现在 GitHub PR 中。每条意见尽量说明：**哪里可能有问题、什么情况下会出问题、依据是什么、建议怎样处理。**

第一版供我们自己的团队使用，只支持指定仓库中的 Python PR。先做出一条可用的完整流程，再考虑开放给更多人使用。

## 2. 它解决什么问题，谁会使用

人工审查代码需要先读懂修改，再找到上下文，最后判断是否有风险。时间有限时，边界条件和异常路径容易被忽略。直接把代码交给 AI，也可能得到位置不准确、缺乏证据或与本次修改无关的意见。

CodeRisk 希望帮助团队更快找到值得检查的位置，并让每条提示更容易核对。

| 使用者 | 原本负责什么 | 系统怎样帮助他 |
|---|---|---|
| PR 作者 | 写代码、解释修改、根据反馈修正问题 | 提前自查，看到具体位置、原因和建议，减少来回沟通 |
| 代码审查者 | 阅读修改、核对问题、提出意见并决定是否批准 | 整理受影响函数和候选风险，提供证据，帮助确定检查重点 |
| 仓库维护者 | 管理仓库、配置审查流程、维护项目质量 | 自动触发审查，查看历史和失败原因，让团队使用统一流程 |

首版主要服务人工审查者，作者和维护者也能使用同一份结果。这三种角色可以由同一个人承担，不需要为它们分别开发三套账号系统。

## 3. 用户怎样使用，系统怎样运行

用户使用浏览器即可，不需要安装桌面客户端。代码保存在 GitHub，分析工作由 CodeRisk 后端完成，网页负责发起和展示。

```text
GitHub PR → 获取修改 → 定位函数与静态检查 → AI 分析
                                            ↓
                             保存报告 → 网页展示 + GitHub 总体评论
```

我们准备提供两种入口，它们共用后面的审查流程。

**手动审查先做通。** 用户打开网页，填写仓库和 PR 编号，点击“开始审查”。系统获取当前修改，显示处理进度，完成后展示报告。后续可以支持直接粘贴 PR 链接，减少填写步骤。

**自动审查随后接入，也属于首版目标。** 维护者先为指定仓库配置接入。有人创建 PR 或推送新提交时，GitHub 通知 CodeRisk；后端再获取修改并自动审查，完成后更新 PR 中的系统汇总评论。

作者和审查者可以一直留在 GitHub 阅读概要，需要完整证据、历史和处理详情时再打开网页。

开发时先在自己的电脑上运行。团队使用时部署一套共享服务，大家访问同一个网页，不需要每个人都配置模型密钥。自动接收 GitHub 事件需要后端持续运行，并能被 GitHub 访问。

## 4. 第一版要完成哪些功能

- **发起审查：** 从网页手动提交指定 PR，也能接收 GitHub 的 PR 更新通知。
- **理解修改：** 获取代码差异，定位受影响的 Python 函数，提供必要上下文。
- **发现候选问题：** 用少量静态规则建立基础检查，再让 AI 分析潜在风险、局部逻辑和异常处理问题。
- **生成可核对的报告：** 显示严重程度、文件位置、代码证据、原因、建议，以及哪些内容未能分析。
- **查看与回写：** 网页提供任务列表、详情和历史，GitHub 中提供总体评论；不同提交的结果能够区分。
- **正确处理失败：** 重复事件不重复审查；AI 失败时保留已有静态结果，明确说明审查不完整；评论发送失败不丢失报告，并能单独重试。

例如，某个函数新增了对用户输入的 `eval` 调用，系统应指出对应位置和代码，解释什么输入可能带来风险，并给出替代方向。

对于逻辑问题，也要说明条件。例如“如果允许空列表，这里可能除零”，而不是在不知道业务约定时直接断言代码错误。

## 5. 我们希望形成什么特色

我们的特色不应只是“把 Diff 发给 AI”。更值得尝试的是以下三个方向。

**让 AI 理解改动发生在什么位置。** 系统先把变更行与 Python 函数关联，再提供相关上下文。希望减少仅看零散修改时的误解，让意见更贴近这次 PR。

**让意见有证据，并检查证据。** AI 需要指出真实文件、位置和代码依据；系统再检查位置是否存在、证据是否匹配，并保留静态规则已经发现的问题。用户可以据此核对，而不必只相信一句结论。

**让用户知道系统分析到了哪里。** 如果部分文件无法解析，或 AI 调用失败，报告仍展示可用结果，同时说明限制。避免把“没有分析成功”误解成“没有发现问题”。

这些是潜在的工程特色，效果需要验证。可以用同一批人工核对过的修改样例，比较“只用静态规则”“直接让 AI 看 Diff”“加入函数上下文和证据检查”三种方式，观察有效发现、误报、定位错误、耗时和费用。

## 6. 第一版的边界

系统辅助人做判断，不保证整个 PR 正确，也不替人决定是否合并。首版不自动修复代码，不执行待审代码，不训练模型，也不支持所有编程语言。

我们先聚焦少量指定仓库和小型 Python PR，做好审查、报告和失败处理。公众注册、多团队管理和更大规模的处理能力留到后续讨论。

## 7. 怎样算第一版做出来了

团队能在一个真实演示仓库中完成这件事：**提交 Python PR，系统获取修改、完成静态与 AI 分析、保存报告、在网页中查看，并把结果发布到 GitHub。**

同时，重复通知不会刷出重复任务；新提交与旧报告不会混淆；AI 或评论发布失败时，用户能看懂发生了什么，并保留已有结果。报告中的意见需要人工核对，不以演示成功代替效果验证。
